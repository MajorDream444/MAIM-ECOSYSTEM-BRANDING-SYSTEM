Sprint 01 — Repository Purpose & Governance

Purpose

Define what GitHub owns inside SOS — and just as importantly, what it deliberately does not.

Core Principle
GitHub owns reusable system definitions — not client data, not private status, not one-off files.
Belongs in GitHub
✓ Component, Template, Workflow definitions
✓ Playbook, Skill, Automation, Data Standard specs
✓ The SOS Foundation Board itself
✓ Naming conventions and schemas
Does Not Belong in GitHub
✕ Live client records
✕ Private operational status
✕ Meeting notes
✕ Exported client PDFs
✕ Design experimentation

Repository Purpose
The single version-controlled home for the reusable SOS architecture — every Component, Template, Workflow, Package, Playbook, Skill, Automation, and Data Standard.
Source-of-Truth Statement
If a definition in Airtable, Notion, or a client document conflicts with what's in sos-core, the repository is correct until a reviewed pull request says otherwise.
What Belongs in GitHub
Reusable system definitions only — Components, Templates, Workflows, Playbooks, Skills, Automations, Data Standards, and the Foundation Board.
What Does Not Belong in GitHub
Live client records, private operational status, meeting notes, exported client PDFs, design experimentation — these live in Airtable, Notion, and Google Drive respectively.
Repository Owner
Operations Lead — accountable for the repository's overall integrity.
Maintainers
Design Lead (Components, Templates), Operations Lead (Workflows, Playbooks, Standards), a designated AI/Automation Lead (Skills, Automations).
Contribution Rules
All changes via pull request; no direct commits to the main branch, including by maintainers.
Approval Authority
The relevant Maintainer approves changes to their domain; cross-cutting changes (e.g. DS-001 schema) require Operations Lead sign-off regardless of domain.
Related Systems
Airtable (live records), Notion (knowledge base), Claude Design (this specification), Google Drive (client files).

GH-003
Conventions

Sprint 03 — Documentation Architecture

Numbering Convention

Two-digit prefix, zero-padded, fixed at creation — a new topic is inserted using a decimal folder (e.g. 04.1-mid-project-changes/) rather than renumbering everything after it.

Navigation Rules

The root docs/README.md links to every numbered folder in order — that file is the single entry point, never a folder listing left to speak for itself.

Internal Linking Rules

Links between docs use relative paths, never absolute URLs, so the documentation set stays valid if the repository is renamed or forked.

README Requirements

Every numbered folder eventually contains its own README.md stating: what this folder covers, which SOS pages it corresponds to, and a table of contents for its files.

Sprint 05 — Schema Architecture

Purpose

Define the machine-readable validation layer that turns Pages 01–10's schemas into something a script can actually enforce.

schemas/ ├── artifact.schema.json # DS-001 base — every other schema extends this ├── client.schema.json # DS-002 ├── project.schema.json # DS-003 ├── component.schema.json ├── template.schema.json # DS-004 ├── workflow.schema.json # DS-005 ├── package.schema.json ├── playbook.schema.json ├── skill.schema.json # DS-006 ├── automation.schema.json # DS-007 └── approval.schema.json
Build order: start with artifact.schema.json's shared metadata fields only. Extend each object-specific schema carefully, one at a time — do not attempt full coverage on day one.
GH-005
Types, Validation & Versioning

Sprint 05 — Schema Architecture

Schema Types

All schemas are JSON Schema documents — chosen because it validates both JSON and YAML metadata files and is readable by nearly every language and CI tool without extra dependencies.

Required Validation Rules

Every schema requires the 13 DS-001 base fields at minimum; type-specific schemas add their own required fields (e.g. template.schema.json requires components_used).

Versioning Rules

Each schema file carries its own $id and version; a breaking change (removing or retyping a required field) increments the major version and requires migrating every existing metadata.yaml that used it.

Relationship Rules

Every object-specific schema uses $ref to extend artifact.schema.json rather than redeclaring the base fields — one definition, inherited everywhere, exactly like DS-001 in prose form.

GH-006
Registry Directory

Sprint 06 — Registry Architecture

Purpose

Create the index that lets any human or agent locate every approved object without walking the entire folder tree.

registries/ ├── components.yaml ├── templates.yaml ├── workflows.yaml ├── packages.yaml ├── playbooks.yaml ├── skills.yaml ├── automations.yaml └── statuses.yaml # canonical status enum, shared by every registry
Registry Types

One flat registry file per object type, each a list of lightweight entries — never the full object content, just enough to locate and reference it.

GH-006
Example Entry

Sprint 06 — Registry Architecture

id: TEMP-001 name: Proposal version: 1.0.0 status: Approved path: templates/commercial/TEMP-001-proposal owner: MAIM Service Operations depends_on: - COMP-001 - COMP-003 - COMP-301
Required Fields

id, name, version, status, path, owner, depends_on — every entry in every registry file, no exceptions and no optional subset.

Status Handling

Status values are drawn only from statuses.yaml's canonical enum (Draft, In Review, Approved, Signed, Void, Expired) — an object cannot be promoted to Approved in its own registry entry without also passing GH's Approval requirements.

GH-008
Branching Model

Sprint 08 — Branching, Review & Approval

Purpose

Define how changes move safely into the official system — deliberately the simplest model that works, not an enterprise branching scheme.

main
Official approved source of truth — protected, no direct commits.
feature/*
New systems, templates, or improvements.
fix/*
Corrections that do not change the system model.
release/*
Optional later, only once formal releases begin.
Three branch types cover everything today; release/* is named here so it has a reserved place, not because it's used yet.

Pull Request Checklist
Metadata validated · README updated if purpose changed · registry entry will regenerate cleanly · naming lint passes.
Status Transitions
Draft → In Review happens on PR open; In Review → Approved happens on Maintainer approval; Approved → merged status is set automatically on merge.

GH-009
Version Meaning

Sprint 09 — Versioning & Change Management

Purpose

Define how SOS evolves without losing history — every object's past state stays reconstructable, never overwritten silently.

1.0.0
First approved version.
1.0.1
Correction with no structural change.
1.1.0
Backward-compatible feature or component addition.
2.0.0
Breaking structural or workflow change.
Breaking-Change Definition

A change is breaking if any existing dependent object (per its depends_on registry entry) would fail Validation against the new version without modification.

GH-009
Change Record

Sprint 09 — Versioning & Change Management

Every Approved Change Identifies
· What changed
· Why it changed
· Objects affected
· Dependencies affected
· Migration required (yes/no, and how)
· Approval owner
· Effective date
Changelog Standard
## [1.1.0] - 2026-07-11 ### Added - COMP-506 Acceptance Certificate variant for Training Package ### Changed - TEMP-005 Welcome Packet: personalization fields expanded ### Migration Required - None — fully backward compatible
Migration-Note Requirements

Any 2.0.0 (breaking) change must ship with a migration note describing exactly how existing dependents update — a breaking change with no migration note fails Validation automatically.

Guide ID

Guide Name
Versioning & Change Management
Semantic Versioning Rules
Every object version follows MAJOR.MINOR.PATCH exactly as shown; a version is never decremented or reused.
Object Version Rules
An object's version lives in its own metadata.yaml and registry entry; both must match at all times or Validation fails.
Repository Release Rules
The repository itself is not versioned as a whole yet — individual objects version independently until release/* branches are introduced (GH-008).
Superseded Status Rules
A superseded object version moves to Void status and archive/ (GH-008); the prior version file is retained, never deleted.
Rollback Expectations
Because merges are squashed per change (GH-008), rolling back a version is a single revert of that change's commit.
Ownership
The object's Maintainer sets its own version bump; a MAJOR bump requires Operations Lead sign-off regardless of domain.
Related SOS Objects
DS-001 Versioning Rules (prose) · GH-006 Registry (version field) · GH-008 Approval Flow
Completion Criteria
Every object has a version matching SemVer, and CHANGELOG.md reflects every merged change with its full record.
Future Enhancements
A bot can auto-draft the changelog entry from a pull request's metadata diff, leaving a human only to confirm accuracy before merge.

Sprint 10 — Integration & Implementation Handoff

Purpose

Define how GitHub connects to the rest of the SOS technology stack — the closing page of the implementation guide.

GitHub
Canonical definitions, schemas, templates, and version history — the source of truth (GH-001).
Notion
Readable manuals, decisions, training material, and explanation — generated from, and linking back to, GitHub docs/.
Airtable
Live clients, projects, statuses, approvals, and payments — synced from GitHub's registries, never the reverse.
Claude Design
Visual foundation, Components, and designed Template references — this project is where the definitions in GitHub are authored and previewed.
Google Drive
Generated client-facing exports and delivery files — outputs, never inputs, to the canonical system.
AI Agents
Read approved definitions from GitHub and produce controlled instances — agents never write directly back to sos-core.
GH-010
Integration Map

Sprint 10 — Integration & Implementation Handoff

GitHub (sos-core) ├──sync──> Airtable # registries/*.yaml → live tables ├──publish──> Notion # docs/ → readable manuals ├──author in──> Claude Design # this project is the design surface ├──generate to──> Google Drive # client exports, never synced back └──read by──> AI Agents # approved definitions only, read-only
Agent Access Rules

Agents (SKILL-XXX, AUTO-XXX) may read any Approved-status object; Draft or In Review objects are invisible to agent access until promoted, so an agent never assembles a document from an unfinished definition.

Export Rules

A generated client document goes to Google Drive, never back into GitHub — client instances live under examples/clients/ only when used as an internal reference sample (GH-007), not as live delivery.
