IMP-001
Vision

Sprint 01 — Vision & Success Criteria

Purpose

Define what "SOS Version 1 Complete" actually means — the finish line every subsequent sprint on this page builds toward.

Success Statement
The MAIM Service Operating System enables every future client engagement to be delivered through one consistent, reusable, AI-assisted operating model.
IMP-001
Objectives & Scope

Sprint 01 — Vision & Success Criteria

Business Objectives
· Reduce time from lead to signed engagement
· Eliminate one-off document creation across proposals, invoices, and reports
· Make every engagement's status visible without asking someone directly
· Let AI agents handle drafting and validation, never final client-facing decisions
Guiding Principles

Implement in the same order the architecture was designed: Foundation and Components first, Automation and AI Agents last — never wire an agent to a system that doesn't have its data model built yet.

Scope / Out of Scope

In scope: implementing Pages 01–14 as real, working systems. Out of scope for Version 1: Creative/Engineering AI departments (AG-010), Stripe/CRM integrations, and any client-specific customization beyond the ten Client Packages already defined.

IMP-002
Risks & Assumptions

Sprint 02 — Current State Assessment

Risks
· Building all three platforms (GitHub, Airtable, Notion) in parallel risks inconsistent field naming — Page 10's Data Standards must be the single reference every builder checks.
· Deploying AI agents before their governing systems exist risks agents operating on incomplete data.
· Team adoption stalls if the system feels heavier than the ad hoc process it replaces.
Assumptions

Existing Platforms: the team already has GitHub, Airtable, Notion, and Claude Design access — this roadmap assumes provisioning these accounts is not itself a blocker.

Technical Debt

None yet — Version 1 has no legacy system to migrate away from, only ad hoc documents and spreadsheets, which simplifies Sprint 03's sequencing considerably.

Dependencies & Cadence

Sprint 06 — Platform Ownership Matrix

Dependencies

Airtable and Notion both depend on GitHub as source of truth (GH-010) — neither Owner may redefine a Template or Component independently; changes route back through Design Lead's pull request review.

Approval Owners

Cross-platform changes (e.g. a new Data Standard field) require both the Design Lead and Operations Lead to sign off, matching GH-001's cross-cutting change rule.

Review Cadence

All five platforms reviewed on the same quarterly cadence established in NT-001/NT-008/AG-007 — one shared calendar, not five separate review schedules.

Risk Register

Sprint 08 — Risk & Readiness Assessment

Purpose

Prepare for launch — consolidating every risk already flagged across IMP-002 through IMP-007 into one register, plus each risk's mitigation.

Template Migration slips (IMP-002/003)
Mitigation: track daily during Phase 1; Design Lead escalates the moment it threatens the 30-day Exit Criteria.
Inconsistent field naming across platforms (IMP-002)
Mitigation: Page 10 Data Standards is the single reference every builder checks before adding a field.
Agent Health Score declines under load (IMP-004/005)
Mitigation: stagger activation, slow cadence rather than push through, per AG-007's review trigger.
Team adoption stalls (IMP-002)
Mitigation: NT-008 training completed before any agent goes live, so the system never feels imposed without explanation.
