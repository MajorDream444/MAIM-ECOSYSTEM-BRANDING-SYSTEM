Notion Knowledge Architecture

GitHub owns canonical system definitions. Airtable owns live operational records. Notion owns explanation, context, decisions, learning, and team knowledge — the readable operating manual.

Notion should help anyone answer: what is SOS, how does this process work, which playbook applies, what decision was made and why, where is the approved source, what changed, and what to do next.

Turn the SOS architecture into a readable, navigable operating manual — the place a human goes to understand why and how, not what the raw definition is.
Knowledge Scope
Explanation, context, decisions, learning, and team knowledge across every SOS page (01–12).

Notion never redefines a Template, Component, or Schema — it links to GitHub for structure and to Airtable for live status, and explains both in prose.
Owners
Operations Lead — overall workspace structure and publishing standards.
Editors

Readers

Publishing Rules
A page is Draft until reviewed; only Approved pages appear in the main navigation and search-surfaced results.
Review Cadence
Quarterly review of every Approved page for accuracy against the current GitHub/Airtable state.
Archive Rules
A superseded page moves to an Archive section with a link to its replacement — never deleted outright.
Related Systems
GitHub (linked definitions), Airtable (linked live records), Claude Design (linked visual references).
Completion Criteria
The workspace exists with Operations Lead as owner, and every team member has Reader access with Editor rights scoped to their domain.

Superseded-Decision Handling

A new decision that overrides an old one links back via Supersedes; the old record's Superseded By field is set automatically and its Status moves to Superseded — never edited to reflect the new choice in place.

Approval Rules

A decision touching a canonical GitHub object (e.g. a Template structure change) requires the same Maintainer sign-off as GH-008's pull request approval — the Decision record and the GitHub PR reference each other.

Handling Rules & Required Output

Sprint 07 — Meeting Notes & Knowledge Capture

Meeting Types
Discovery, Kickoff, Weekly Sync, Milestone Review, Internal — matching the meeting touchpoints across WF-001–010.
Action-Item Handling
Each Action Item carries an owner and due date; unresolved items roll forward into the next Meeting Note automatically rather than being lost.
Decision Extraction
Any line marked as a Decision creates a linked Decisions database record (NT-006) with Related Evidence pointing back to this Meeting Note.
Risk Extraction
Risks feed directly into SKILL-005's risk log (AT-004 Project Health Status) rather than staying siloed in the note.
Follow-Up Rules
A Next Meeting date is required for any note whose Action Items remain open — no meeting note closes without a stated next checkpoint.
Archive Process
Meeting Notes are never archived — they remain a permanent record, searchable by Related Project or Client indefinitely.
AI Assistance Opportunities
AUTO-007 Knowledge Automation drafts the entire Meeting Note from a transcript; a human confirms Decisions and Action Items before the note is marked final.
Completion Criteria
The Meeting Notes database exists with all 16 fields, and the Decision/Risk extraction links are configured to the Decisions database and Airtable respectively.

Process & Required Output

Sprint 09 — Research, Lessons & Continuous Improvement

Improvement Intake Process
Any team member can log a Lesson via the Lessons Learned database (NT-004); Pattern Identified requires the Owner to see the same root cause recur across 2+ Lessons before proposing a Change.
Review Cadence
Lessons are reviewed at the same quarterly cadence as NT-001/NT-008, alongside PB-010's Internal Operations Playbook KPI review.
Approval Process
A proposed Change becomes a Decision record (NT-006); Decision Approved is the same approval gate as GH-008's pull request review when GitHub objects are affected.
Relationship to GitHub Changes
GitHub Updated corresponds to a merged pull request referencing the Decision ID in its commit message.
Relationship to Airtable Operations
If the Lesson points to an operational gap (not a definition change), the fix lands directly in Airtable's automation rules (AT-010) instead of GitHub.
Completion Criteria
The Lessons Learned database exists with all 13 fields, and the cycle from Observation through Team Notified is documented as a linked walkthrough page.
