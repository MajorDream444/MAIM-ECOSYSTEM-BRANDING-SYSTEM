Sprint 01 — Base Purpose & Governance

Airtable Guide ID
AT-001
Base Name
MAIM Service OS
Base Purpose
The single live operational record for every active Client, Project, Artifact, and their current status — Airtable answers "what's happening now," GitHub answers "what is the system."
Operational Scope
Everything with a status that changes day to day: clients, projects, artifacts, approvals, milestones, and payments.
Source-of-Truth Boundaries
Airtable is authoritative for current state; GitHub is authoritative for what a Template, Workflow, or Component is structurally. Airtable references GitHub IDs, never redefines them.
Owners
Operations Lead — full schema and permission control.
Editors
Engagement Leads and Finance — record-level edit rights within their assigned Clients/Projects.
Viewers
All internal team members; clients never get direct base access — they see assembled documents only.
Data Governance Rules
No canonical definition (Template structure, Component spec) is ever recreated as an Airtable field — those stay referenced by ID only.
Related Systems
GitHub (sos-core, read-only source), Notion (linked knowledge), Google Drive (linked exports), Gmail/Calendar (linked automations).
Completion Criteria
The base exists with Operations Lead as sole schema owner, and every internal team member has appropriate Editor/Viewer access assigned.

Sync Rules & Example

Sprint 05 — Templates, Components & Workflows Tables

Sync Rules

A scheduled import reads registries/*.yaml (GH-006) and upserts these three tables; any manual edit to a synced field is overwritten on the next sync rather than preserved — Airtable is not the place to correct a Template definition.

GitHub Reference Fields

GitHub Path links directly to the object's folder (GH-004); Claude Design Reference links to the DC file where the Template's visual definition lives.

Example Record
Template ID: TEMP-001 Template Name: Proposal Version: 1.2.0 Status: Approved GitHub Path: templates/commercial/TEMP-001-proposal/ Components Used: [COMP-001, COMP-003, COMP-301, COMP-501] Related Workflows: [WF-002, WF-003]

References & File Location

Sprint 06 — Artifact Registry

File-Location Rules

The Artifact record never stores the file itself — Google Drive File links to the actual PDF, living under the client's folder per DS-009's file convention.

Reference Fields
GitHub Reference — links to the Source Template's canonical definition, not the Artifact itself
Notion Reference — links to any related knowledge base entry (e.g. meeting notes that produced it)
Google Drive File — links to the actual generated document
Related Artifacts — other Artifacts this one supersedes, references, or is referenced by
Dependencies — Artifacts that must exist before this one can be generated (e.g. Agreement before Invoice)
Next Action — what happens to this Artifact next (e.g. "Awaiting client signature")
Version Handling

A new version creates a new linked record rather than overwriting the field — Related Artifacts shows the version chain, so v1.0 is never lost when v2.0 supersedes it.

Review Gates, Views & Example

Sprint 07 — Milestones, Tasks & Approvals

Review Gates

A Milestone with Approval Required = true cannot move to Status = Complete until its linked Approval record reaches Approved — enforced by an Airtable automation, not manual discipline.

Views

Upcoming Milestones (Due Date within 14 days), Awaiting Approval (Approval Status = Awaiting Approval, sorted by Requested Date), Rejected/Revision Needed (escalation view).

Priority Automations

Sprint 10 — Airtable Automations & Integration Map

Purpose

Define how Airtable becomes the operational control center — the closing sprint of Page 12.

New Client Created
→ Generate Client ID
New Project Created
→ Generate Project ID → Create default Milestones
Proposal Approved
→ Update Engagement Status → Start Agreement workflow
Payment Marked Paid
→ Create Receipt Artifact record → Start Onboarding workflow
Milestone Completed
→ Create Approval request
Approval Granted
→ Activate next Milestone
Project Completed
→ Start Closeout workflow → Flag Case Study opportunity
Human Approval Points: Milestone Completed only creates the Approval request — it never sets Approval Status to Approved automatically. Error Handling: any automation that can't resolve a linked record (e.g. no matching Client) logs to a Failures view rather than creating an orphaned record.

Phases & Page Completion

Sprint 10 — Airtable Automations & Integration Map

Implementation Phases
1. Build all ten core tables (AT-002 through AT-008) with fields and links only, no automations yet.
2. Connect the GitHub registry sync (AT-005) so Templates/Components/Workflows populate automatically.
3. Turn on the seven Priority Automations one at a time, verifying each against its logged Failures view.
4. Build the five interfaces and dashboards (AT-009) once live data exists to populate them meaningfully.
5. Connect Gmail and Google Calendar integrations last, once the underlying data is trustworthy.
