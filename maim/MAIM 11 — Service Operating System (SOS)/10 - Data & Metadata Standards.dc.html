Sprint 01 — Universal Artifact Metadata

Purpose

Define the metadata every SOS artifact must contain — the base schema every other Data Standard on this page extends.

Required Fields
Artifact ID
Unique identifier following the SOS naming convention, e.g. DOC-2026-00417.
Artifact Type
One of: Template, Component, Workflow, Journey, Package, Playbook, Skill, Automation, Standard.
Client ID
Reference to the owning client record; em-dash if internal-only.
Project ID
Reference to the active engagement this artifact belongs to.
Workflow ID
The WF-XXX this artifact was produced under, if any.
Template ID
The TEMP-XXX this artifact was assembled from, if any.
Version
Semantic version string, e.g. v2.3, per the Versioning Rules below.
Status
One of the standard SOS status values: Draft, In Review, Approved, Signed, Void, Expired.
Owner
Named individual accountable for the artifact.
Created Date
ISO 8601 date the artifact was first generated.
Updated Date
ISO 8601 date of the most recent revision.
Approval State
Free-text or fraction summary, e.g. "2 of 3 approved."
Confidentiality
One of: Public, Internal, Confidential — Client & Internal, Restricted.
Optional Fields

Effective Date, Related Artifacts (array of Artifact IDs), Skill ID (if AI-generated), Automation ID (if system-generated), Tags (free-text array for search).

DS-001
Conventions & Example

Sprint 01 — Universal Artifact Metadata

Naming Convention
COMP-XXX Components
TEMP-XXX Templates
WF-XXX Workflows
CJ-XXX Client Journey
PKG-XXX Packages
PB-XXX Playbooks
SKILL-XXX Skills
AUTO-XXX Automations
DS-XXX Data Standards
DOC-YYYY-NNNNN Client Documents

All library object IDs use a three-digit sequence (001–999) within their prefix; client document IDs use year + a five-digit running number, never reused.

Versioning Rules

Major version (v2.0) increments on a scope or pricing change; minor version (v2.3) increments on wording, formatting, or non-substantive edits. Signed documents are never re-versioned in place — a new version supersedes and the prior one is archived, never deleted.

Example Metadata Block
artifact_id: DOC-2026-00417 artifact_type: Statement of Work client_id: CLIENT-0142 project_id: PROJ-0088 workflow_id: WF-003 template_id: TEMP-002 version: v2.3 status: In Review owner: J. Alvarez created_date: 2026-06-02 updated_date: 2026-07-08 approval_state: 2 of 3 approved confidentiality: Confidential — Client & Internal related_artifacts: [PROP-2026-00398, MSA-2025-0091]

Sprint 02 — Client Data Standard

Purpose

Standardize every client record so CRM, Airtable, and every automation reference the same fields the same way.

Required Fields
Client ID
Unique identifier, e.g. CLIENT-0142, assigned at first CRM record creation (AUTO-001).
Company
Legal or trading name used consistently across every client-facing document.
Primary Contact
Name, role, email, and phone of the client's main point of contact.
Industry
Standard industry tag, used for case study and Package-fit pattern matching.
Package
Current active PKG-XXX; historical packages retained in Projects, not overwritten.
Status
One of the Status Lifecycle values below.
Status Lifecycle
Lead
Qualified
Active
Support
Dormant
Churned

Status only ever moves forward automatically (WF-001 through WF-010 advance it); moving backward (e.g. Active to Dormant) always requires a human-logged reason.

Milestones, Dependencies & Example

Sprint 03 — Project Data Standard

Milestones

An ordered array of Milestone objects (COMP-402), each with a name, due date, Gate Indicator status, and Approval Record reference (COMP-501) once cleared.

Dependencies

A directed list of prior Milestones that must be Approved before the next can start — enforced by SKILL-005, not left to manual tracking.

Deliverables

An array of named deliverables per Milestone, each linked to its file location and Acceptance Criteria — the same list SKILL-007 QA validates against at Closeout.

Example Project Record

Alvarez start_date: 2026-06-15 end_date: 2026-09-30 current_phase: Implementation current_workflow: WF-007 health_status: On Track milestones: [M1-Discovery (Approved), M2-Blueprint (Approved), M3-Rollout (In Progress)]

Schema

Sprint 04 — Template Metadata Standard

Purpose

Ensure every template — TEMP-001 through TEMP-010 and any future addition — follows one consistent structural definition.

Required Fields
Template ID
TEMP-XXX, assigned once at creation, never reused.
Template Name
Human-readable name shown on the Template Library catalog page.
Purpose
One-sentence statement of what the template exists to accomplish.
Audience
Who receives the assembled document — Prospective Client, Active Client, Internal.
Lifecycle Stage
Which stage of the client relationship the template belongs to.
Current Version
The template's own version, distinct from any document generated from it.
Version Rules

A Template version increments only when its structure or required Components change — not when a generated document's content changes. Every document generated records which Template version it was built from, so historical documents remain interpretable even after the Template evolves.

DS-004
Dependencies & Example

Sprint 04 — Template Metadata Standard

Components Used

An explicit array of COMP-XXX references — the same list shown on each TEMP-XXX's "Components Used" page. A Template cannot ship without every listed Component existing in the Component Library.

Related Workflows

One or more WF-XXX references indicating which Workflow step(s) generate a document from this Template — enforced by SKILL-007 QA at generation time.

Example Template Record
template_id: TEMP-001 template_name: Proposal purpose: Present a recommended solution, scope, timeline, pricing, and next steps audience: Prospective Client lifecycle_stage: Proposal current_version: v1.2 components_used: [COMP-001, COMP-003, COMP-101, COMP-202, COMP-301, COMP-401, COMP-501, COMP-701, COMP-901] related_workflows: [WF-002, WF-003]

Schema

Sprint 05 — Workflow Metadata Standard

Purpose

Standardize workflows so every WF-XXX in the library can be read, validated, and eventually executed the same way by any system.

Required Fields
Workflow ID
WF-XXX, sequential, never reused.
Workflow Name
Human-readable name shown on the Workflow Library catalog page.
Purpose
One-sentence statement of what the workflow converts or advances.
Trigger
The precise Project or Client Status change that starts this workflow — never a vague "when appropriate."
Inputs & Outputs

Inputs are the prior workflow's Outputs, named explicitly (e.g. WF-002's output "Approved Proposal" is WF-003's input). Outputs are the state changes and artifacts this workflow produces, each traceable to a Template or a Status field change.

DS-005
Decisions, Automation & Example

Sprint 05 — Workflow Metadata Standard

Decision Points

Any branch or loop in the flow (e.g. WF-003's Revisions loop) recorded explicitly with its condition, so an automation or agent can evaluate it rather than guessing intent from prose.

Automation References

Every AUTO-XXX that executes some or all of this workflow, listed explicitly — a workflow with no Automation reference is understood to be fully manual today.

Example Workflow Record
workflow_id: WF-004 workflow_name: Agreement to Payment purpose: Move from a signed agreement to a paid invoice and issued receipt trigger: Agreement Signed (WF-003 output) inputs: [Signed SOW, Signed Agreement] outputs: [Invoice, Receipt] decision_points: [] automation_references: [AUTO-003, AUTO-004]

Sprint 06 — Agent Skill Metadata Standard

Purpose

Standardize every AI capability so any agent framework — Claude, ChatGPT, or a future orchestrator — can discover and invoke SOS Skills the same way.

Required Fields
Skill ID
SKILL-XXX, sequential, never reused.
Skill Name
Human-readable name shown on the Agent Skill Library catalog page.
Purpose
One-sentence statement of the capability this Skill provides.
Trigger
The precise condition or event that should invoke this Skill.
Required Inputs

A typed list of what the Skill needs to run — each input traceable to a Template, Project, or Client field, never a free-text "context" blob.

Outputs

What the Skill produces — a draft document, a structured recommendation, or a data update — each named the same way it appears in the Skill's own Page 08 spec.

DS-006
Limitations, Review & Example

Sprint 06 — Agent Skill Metadata Standard

Limitations

Explicit statement of what the Skill must never do unattended — e.g. SKILL-004 never sends a mismatched Invoice, SKILL-002 never sends a Proposal without Internal Review.

Human Review Rules

Every Skill declares whether its output requires review before use (most do) or can proceed unattended (only SKILL-004's standard-path invoice matching qualifies today).

Example Skill Record
skill_id: SKILL-002 skill_name: Proposal Skill purpose: Generate Proposal Version 1 for human review trigger: Discovery Report reviewed and Package matched required_inputs: [Discovery Report, Client Package, Pricing Inputs] outputs: [Proposal v1 Draft] limitations: [Never sends directly to client; never overrides Package pricing without escalation] human_review_required: true

Automation Name
Human-readable name shown on the Automation Library catalog page.

Systems

DS-007
Error Handling, Logging & Example

Sprint 07 — Automation Metadata Standard

Outputs

What the automation produces or changes — matched exactly to its Outputs field on Page 09, so a system integrator knows precisely what to expect back.

Error Handling

Explicit failure behavior — retry once, hold for manual reconciliation, or halt and notify — never "fail silently" in any automation on this system.

Logging

Every run is logged with timestamp, trigger source, and outcome (success, blocked, failed) — the raw material PB-010's KPI review draws on monthly.

Example Automation Record
automation_id: AUTO-004 automation_name: Payment Automation trigger: Stripe payment webhook confirms payment systems: [Airtable, Gmail, Stripe (future)] conditions: [if payment matches an open Invoice -> proceed; if unmatched -> hold] outputs: [Paid Invoice, Issued Receipt, Updated Financial Record] error_handling: Unmatched payment held for manual reconciliation, never auto-matched by guess logging: timestamp, trigger_source, outcome recorded per run

DS-009
File, Folder & Platform Conventions

Sprint 09 — Naming Convention Standard

File Naming
{ARTIFACT_ID} {Document Type} v{version}.pdf e.g. DOC-2026-00417 Statement of Work v2.3.pdf
Folder Naming
{CLIENT-ID} {Company Name}/ {PROJ-ID} {Project Name}/ Contracts/ Invoices/ Deliverables/ e.g. CLIENT-0142 Aurelia Capital Partners/PROJ-0088 Q3 Advisory/
GitHub Conventions

Repository names use lowercase-kebab-case matching the object prefix, e.g. sos-component-library, sos-automation-library. Branch names reference the ID being worked, e.g. auto-004-payment-automation.

Notion Page Names

{ID} — {Name}, exactly matching the catalog entry on its SOS page, e.g. "PB-004 — Weekly Operations Playbook."

Airtable Record Naming

The primary field of every table is always the ID itself, not the name — sorting, filtering, and linking all key off the ID; the Name lives in a secondary field for human readability.

Dictionary A–M

Sprint 10 — SOS Data Dictionary

Purpose

Create the official vocabulary of the Service Operating System — the closing entry that ties every prior page's terms into one shared reference.

Artifact
Any generated document or record with SOS metadata (DS-001). Related: Template, Workflow. Owner: Engagement Lead. Example: DOC-2026-00417.
Automation
A system-executed sequence connecting a trigger to a measurable outcome (DS-007). Related: Skill, Workflow. Owner: Operations. Example: AUTO-004.
Client
A company or individual with an active or historical MAIM engagement (DS-002). Related: Project. Owner: Engagement Lead. Example: CLIENT-0142.
Component
A reusable design element with defined layout, type, and spacing rules (Page 02). Related: Template. Owner: Design. Example: COMP-501.
Deliverable
A named, scoped output tied to a Milestone, tracked through to Acceptance. Related: Project, Milestone. Owner: Engagement Lead. Example: "Phase 1 Report."
Milestone
A scoped checkpoint within a Project's Timeline, gated by Approval (COMP-402/404). Related: Project, Approval. Owner: Engagement Lead. Example: "M2-Blueprint."
DS-010
Dictionary P–W

Sprint 10 — SOS Data Dictionary

Package
A pre-assembled combination of Templates, Workflows, and pricing sold as a unit (Page 06). Related: Client, Template. Owner: Sales/Engagement Lead. Example: PKG-002.
Playbook
A step-by-step human execution guide for running a repeatable process (Page 07). Related: Workflow, Skill. Owner: Operations. Example: PB-004.
Project
A single active or completed client engagement (DS-003). Related: Client, Workflow. Owner: Engagement Lead. Example: PROJ-0088.
Skill
A reusable AI capability with defined inputs, outputs, and review rules (DS-006). Related: Automation, Playbook. Owner: Operations. Example: SKILL-002.
Status
The current lifecycle state of any Artifact, Client, or Project, drawn from a fixed enumerated list. Related: all objects. Owner: system-enforced. Example: "In Review."
Template
A fixed document structure assembled from Components (DS-004). Related: Component, Artifact. Owner: Design. Example: TEMP-001.
Workflow
A defined internal sequence with a trigger, steps, and an output (DS-005). Related: Project, Template, Automation. Owner: Operations. Example: WF-004.
